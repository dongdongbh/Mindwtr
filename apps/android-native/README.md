# Android native development app

This isolated Compose app uses `tech.dongdongbh.mindwtr.nativeclient.dev` and its own private `mindwtr-native-dev.db`. It does not read or replace the React Native app. It has RN's tabs: **Inbox**, **Focus**, the quick-access tab (**Review**, **Contexts**, **Calendar**, or **Projects**, as core's setting names), and **Menu**. Each list shows its first 50 rows, loads more in windows of at most 50, and calls the shared core contract to capture, complete, and edit tasks. The app syncs with WebDAV and the self-hosted Mindwtr cloud (see Sync below); it has no fixture seeding or production upgrade path; its entry points from outside the app (links, text shares, assistant notes, RN's app shortcuts, the capture intent and context automation) are described below.

Every word on screen comes from core. At boot the app calls core's `setLanguage` with the React Native app's saved language (AsyncStorage `mindwtr-language`, read by the upgrade build's guard; none in the dev build) and the device locale, then reads one label map through `getStrings`. The keys are the ones mobile uses for the same controls (`Labels.kt`). Core fills in English for a key a language lacks; a key core does not know shows as the key and is logged once. Core has no key for "Refresh", "Load more", "Reload", or "Storage unavailable", so the app uses **Try again** (`common.retry`) for a failed read and for the editor's reload, **More** (`common.more`) for the next window, and shows a failed boot as its message alone.

The app looks like the React Native app, so an RN user recognizes it at once: RN's header, RN's bottom tab bar (Focus, Inbox, the center capture button, the quick-access slot, and Menu), RN's theme tokens (`Theme.kt`, the only file with colors), RN's lucide icons (`Icons.kt`), and RN's task row (`TaskRowView.kt`). A row shows core's meta line as core sent it (project or area dot, contexts, the due date in the user's format and core's urgency color, the checklist count; detail parts stay hidden, as in RN's lists and default Focus), core's priority strip, and core's TalkBack label. A swipe right reveals RN's labelled action button for the row's status (Done, Next, or Restore, from core's row meta): a tap runs it and a long-press opens RN's status menu, as in RN. TalkBack has the same action and Change Status as custom actions; there is no Done button, as in RN. The Inbox shows RN's status glyph and a project shows RN's status badge; a tap opens RN's status menu, which saves through core's `updateTask`. The header's left side is RN's area switcher (`AreaSwitcher.kt`): core's `getAreaFilter` label, and RN's sheet, where a tap sends core's `next` selection through `setAreaFilter`. A refused star shows core's text in RN's toast. The capture button opens RN's capture popup (`CaptureScreen.kt`) on core's quick capture contract (`native-host-contract-quick-capture.ts`): Add Task and Close, the field with core's live preview, the project or contexts chip with Focus and More, More's panel (the note, the Focus, due time, contexts, area, project and priority chips with RN's pickers, the syntax help, and Today, Tomorrow, Next week and Custom; the Custom date and due time pickers open on core's day and time), and RN's Add another switch (RN's Android switch: a raised thumb on a faint track; kept on the device under RN's key) with Save & edit and Save. Every chip and picker row sends the edit core put on it. Several lines ask core's question; Create tasks writes core's recovery snapshot under `files/snapshots` (as mobile does: a temporary file, a clash number, the 5 newest) and then one task per line in one write; the batch sends the name actually written, which is on disk with the request, so a retry sends the same snapshot and a stale one is replaced with a new snapshot and the same capture UUIDs. Each save's exact request (a capture UUID, one per line for several lines) is written to a synced file in the no-backup folder before the call; a failed one keeps its exact retry, and after process death it is sent again before anything else, so core writes it once. A refused date command shows core's notice and keeps the draft. The popup's draft (text, options, open picker, and chip edits not yet answered) survives rotation and process death; a request whose outcome was lost comes back even after a force-stop. Close discards the draft, as RN does. In portrait only More's panel scrolls, as in RN; in landscape everything under the header scrolls, so Save & edit and Save stay reachable above the keyboard. More's panel has RN's Import .txt: the system's picker for a text file; core plans the file's text (`planQuickCaptureImport`): several lines ask core's question and Create tasks sends the file's text (on disk with the question, as the popup's own lines), one line goes into the field, and a file it cannot read shows core's notice. RN's microphone is not built. The theme is RN's choice as core resolves it: the synced `settings.theme`, else RN's device-local `@mindwtr_theme` (read by the upgrade build's guard), else the system's light or dark mode.

Each screen scrolls as one list, so landscape shows rows rather than fixed controls. The Inbox is RN's task list on core's `getInboxView`: its first items are RN's Sort, Group and Filters controls (Filters in the tint with core's count while filters are on) with the Mind Sweep pill beside them, the active filters with Clear, RN's **Process Inbox (N)** button (core's label, 99+ above 99; TalkBack hears core's exact count), and core's "All areas" line. An empty Inbox shows Mind Sweep in the button's place. Mind Sweep (the pill, the button, and the Weekly Review's links) opens RN's full-screen Mind Sweep on core's `getMindSweep` and `addMindSweepItem`: core's title and Close, the intro with core's scope chips and Start, one cue list at a time (its title and progress, the prompts, the capture box with Add, core's failure line, what was captured in it, Back and Next), and the summary with Finish. Each control carries core's scope or step. Add waits for core's answer on the text as typed, then sends it with a request UUID that becomes the Inbox task's id; the request is in a synced file in the no-backup folder before the call, so a failed Add keeps its exact retry and a lost answer is sent again first after process death. The screen state (scope, step, captures, the text, the failure line) is in a synced file while Mind Sweep is open, so rotation and process death keep it; Close and Finish forget it, as RN's modal does, and return to the screen it opened over. Sort is the stored task-list sort (`setTaskListSort`); the grouping and the filters are RN's session choices; a folding heading keeps core's folds for its grouping under RN's `mindwtr:view:group-collapse:inbox:v1`. Only the header, the tabs, a failure message with its retry, and the bulk bar while selecting stay fixed.

A long-press on a row of the Inbox, Waiting, Someday, Reference or Done starts RN's selection mode on core's `getBulkActions` and `runBulkAction`: a tap toggles a row (core keeps the tap order and Range's anchor), and RN's bulk bar shows core's count, core's statuses to move to, Move to section… (Someday), Bulk organize (the Inbox), Range, Add tag, Remove tag, and Delete, which asks core's question first and whose toast has core's Undo. The bar also offers core's stateless Select all (RN's lists have none; the contract has it, as Archived does): core resolves it again for the action and refuses it once the rows changed. Bulk organize is RN's dialog on core's draft: every chip, picker row, quick date and typed field sends core's edit, and Apply sends the draft core answered. An action that changed something leaves selection mode; Back leaves it too. Read-only rows (an archived project's) never select.

The header's search button opens RN's global search on core's `searchTasks`: the field, Clear, RN's filter sheet (due date, location, contexts and tags, Include, status, scope, area, all core's words and choices), the active chips that clear a filter, core's truncation and hidden-matches lines, and the project and task results with core's highlights and date line. A task opens the editor over the search, and, as RN's highlight, its row on the list it opened on (the one under the search) is outlined in the tint until 3.5 s pass or that list is left; a result core cannot open there goes to its list (Inbox, Focus, a project, or the Menu tab's Waiting, Someday, Reference, or History's Done or Archived). Clearing an active chip removes its filter value, so a second tap changes nothing. Mark Done is the lists' Done. Save Search saves through core's `saveSearch`: the submitted query, name and request UUID are kept with the screen before the call, the dialog stays locked to them until core answers, and after process death they are sent again before it unlocks. Save Search stays on the search (RN then opens the saved search's screen; not wired yet). An answer for an older query is dropped by core's echoed query.

**Process Inbox (N)** opens RN's step flow on core's session (`startInboxProcessing`, `getInboxProcessingStep`, `commitInboxProcessingStep`, `skipInboxProcessingTask`, `endInboxProcessing`): the progress header with Close, RN's guided/quick switch (kept on the device under RN's key `mindwtr:view:inboxProcessingMode:v1`) and Skip; the item's card with its editable title and note; then core's step, drawn from core's view, where every chip, date, and suggestion sends the exact edit core put on it, one at a time. Each answer (a choice, File it, Back, Skip) is a command with a request UUID: it is written to a synced file in the no-backup folder before the call, a failed one keeps its exact retry through rotation and a new screen. After process death the app lands on the Inbox, as RN does, and the owed answer is sent again in the background: core's session died with the process, so core refuses it without writing and its message shows. The record on disk goes only after core acknowledges or refuses the answer, so another death during that replay finds it again. Core refuses a new session while earlier writes are unsaved; its message shows. The failure message is drawn above the list and is a live region, so TalkBack always reaches it.

The **Menu** tab opens RN's More sheet on core's `getMoreMenu` (RN's `MoreNavigationSheet`): over the list and above the tab bar, a dimmed backdrop and a card with RN's handle, core's utilities (Trash, Board, History, Settings), core's saved searches, and core's six tiles, with RN's Ionicons in core's colors. A drag down, the backdrop, Back, the Menu tab again, another tab, or the capture button closes it. Waiting, Someday, Review, Reference, Contexts, Calendar, Board, History, Trash, Projects, Settings, and the saved searches open. A saved search opens RN's screen on core's `getSavedSearchView` under RN's stack header (Search): its name, its query, and Delete (RN's red trash), which asks core's question and then sends core's `deleteSavedSearch` and goes back; core's rows with the lists' own swipes, status menu and editor (windows of 50, **More**); and core's empty line, with core's Inbox and Back when the saved search is gone.

The quick-access slot of the tab bar holds the view core's `quickAccessView` names, as in RN: **Review** (RN's default), **Contexts** or **Calendar** show that screen under the tab header, and Projects then moves to the More sheet, where its tile opens RN's Projects screen (a parked, archived, or searched project opens there too). Any other value shows Projects. The app reads the sheet at boot, so the tab bar draws the right tab from its first frame. A destination opens full screen over the tabs, as RN pushes it, under RN's stack header (Back and the title); Back returns to the tabs. Each list reads core's view in windows of 50 (**More** at the end) and each collection (people, parked projects, filter tokens and projects, saved searches) in core's windows of 100 through `getMenuViewCollection`, under the view's revision; a view that changed between windows is read again from its first window. Rows are RN's task row with RN's status glyph, and every list is read again on resume and after every command.

Differences from RN on purpose: the bulk bar of the Inbox, Waiting, Someday, Reference and Done offers core's stateless **Select all** (RN's task lists have none; the contract offers it, as Archived's bar has); on Focus's reorder screen only the dragged row moves and shows its new place (RN also slides the other rows aside; the stored order is the same); Mind Sweep's Back and Next go to the step core put on the control, so a quick double tap moves one step (RN's functional update moves two); Mind Sweep keeps text typed while an Add was with core (RN empties the box anyway); and a failed bulk action shows the failure message with its exact retry rather than RN's "failed" toast, as every write here does.

**Entry points** (`EntryPoints.kt`, core's `resolveNativeEntryPoint` in `native-host-contract-entry-points.ts`). The app's public component is RN's name, `<applicationId>.MainActivity`, an alias of the (singleTask, as RN's) activity, so home-screen icons, pinned shortcuts and widgets that launch RN's name find it. It carries RN's entry points: the launcher, links of the build's scheme (`mindwtr-native-dev` in the development build, so RN's app on the same phone keeps `mindwtr://`; `mindwtr-upgradetest` in the harness build; `mindwtr` in a release), text shares (`SEND` `text/plain`), Google Assistant's notes (`CREATE_NOTE`), and RN's app shortcuts, generated from RN's own plugin (`scripts/build-shortcuts.mjs`) with RN's ids and labels on the build's scheme. Kotlin reads only the intent's data and its text extras as strings and sends them to core, which answers as RN's root layout would: RN's route (a tab, a Menu screen, the Projects screen with a project, Focus with a task opened in the editor on its View tab and outlined, or the global search with its query and Include completed), core's toast (a capture link without a title, a share with nothing readable), RN's capture screen with the route params RN pushes to it (a capture link's or an assistant note's title, note, tags and project; a share's title and description, as RN's email-subject rule builds them; a widget's quick capture, `capture-quick`), or the capture popup (the capture feature, `open-feature?feature=capture`, as RN's tab route opens it). **The capture screen** (`CaptureModal.kt`, `CaptureModalModel.kt`, core's `native-host-contract-capture-modal.ts`) is RN's `capture-modal.tsx`: the Add Task card centered on the background (in the space above the keyboard while it is up, so Cancel and Save stay reachable), the hide-keyboard button while the keyboard is up, the ? button (core's syntax help), the title field (focused after 120 ms, as RN's; Return adds a line) with core's preview chips, the description field when the entry brought one, RN's failure line, and Cancel, Save & edit (the task's editor on its Task tab replaces the screen) and Save (RN's fixed blue). A capture link's tags and project stay the screen's props: core saves the tags as tags, files the task in the project (matched by id or title, created when none matches), and never puts them in the title. Several lines ask core's question on the screen; Create tasks writes one task per line in one write. Every write request is journaled before the engine sees it (`core/WriteJournal.kt`, under `files/journal`): `CoreHost.callAsync` writes the method and its exact arguments (request UUID included) to a temporary file, syncs it, renames it into place and syncs the folder. Debug builds read four fault properties before each write command, and the language, the intl check and two net check properties at boot; release builds never read them:

- `debug.mindwtr.native.fail_commit=1` makes every SQLite `COMMIT` fail.
- `debug.mindwtr.native.delay_before_ms=<ms>` holds the command before it runs.
- `debug.mindwtr.native.delay_after_ms=<ms>` holds the acknowledgment after the commit.
- `debug.mindwtr.native.journal_stop=<at>:<op>` kills the process during the write `<op>` (the host method, or a Menu command's name): `before` right after its journal entry is on disk, `after` right after core's reply, before the entry is settled. A replay never stops.
- `debug.mindwtr.native.language=<code>` replaces the saved language (for example `zh`) for the next process, so a check never changes the phone's language.
- `debug.mindwtr.native.net_check=<port>` runs the net check below once, after boot, against `http://127.0.0.1:<port>`. Its last phase stops the host on purpose, so that boot then fails.
- `debug.mindwtr.native.net_max_bytes=<bytes>` lowers the fetch response limit for the next process, so the net check can test the refusal.
- `debug.mindwtr.native.intl_check=1` logs the intl check's cases below once, while the next process loads its bundle.

The JS host has RN's `fetch` and secure storage: sync uses both, and the AI and calendar passes will. `fetch` (`host-polyfills.js`: `Headers`, `Request`, `Response` with `text`, `json`, `arrayBuffer`, `bytes` and `clone`, `AbortController`, `AbortSignal.abort` and `AbortSignal.timeout`) hands each request to `HostIo.kt`, which runs it on OkHttp, as RN's fetch does (the same redirects, TLS, cleartext rule from RN's network security config, RN's 10 s connect timeout, and a 5-minute ceiling, as RN's background-safe fetch); the answer settles in the engine's pump loop, where timers fire. Methods: GET, HEAD, POST, PUT, DELETE, PATCH, PROPFIND, MKCOL, MOVE and COPY; bodies as text or bytes. A body may be as large as core's largest limit (a 1 GiB sync document), bounded by a fifth of the app's heap; core applies its own smaller limits. A response is the whole body or a rejected fetch, never a short body, and a HEAD, 204 or 304 labelled gzip has nothing to decode. Text is fatal UTF-8: a `TextDecoder` made without options, and `Response.text()`, throw on bytes that are not UTF-8, so a damaged body never reads as other text (`{ fatal: false }` replaces them, as the platform does). A host operation has a deadline: 30 s (core's storage and request timeouts), or 5.5 minutes for one that sends requests. Past it the operation's signal fires, its fetches reject, and new fetch and secret calls are refused while it ends (sync's secret calls are not: a Save running beside it would otherwise stop half-way and leave sync off); one that does not end within 10 s stops the host, so it never resumes. Unlike RN, a request with `redirect: 'error'` (core's PUT, POST, PATCH and DELETE) refuses a redirect, as desktop's fetch does. `__mindwtrSecrets.getSecret`, `setSecret` and `deleteSecret` (`SecretStore.kt`) keep values in RN's expo-secure-store format (the `SecureStore` preferences file, `key_v1-<key>`, the Android Keystore AES-GCM key RN uses), so an in-place upgrade reads the secrets RN saved.

The `upgradetest` build type (`./gradlew :app:assemblePlayUpgradetest`) is for the upgrade harness only. It installs as the throwaway package `tech.dongdongbh.mindwtr.upgradetest` over a real RN v1.3.2 build and opens the RN database, `files/SQLite/mindwtr.db`. Before anything opens that file, a guard refuses to start when the database is missing while other RN state exists and RN AsyncStorage (`databases/RKStorage`) holds no JSON backup, when that backup is over 64 MB, or when either file cannot be read or the database fails `quick_check`. The guard reads byte copies in the cache folder, never the files themselves. On a refusal the app shows the refusal message and changes no file. Otherwise the JS host imports the backup as RN's next launch would (core `planLegacyJsonImport`: the `mindwtr-data:json-ahead-of-sqlite` marker, the one-time reconcile, or an empty or missing database). After the import is saved and read back with every field equal, the guard copies `RKStorage` once to `files/SQLite/RKStorage.prewrite/`, then deletes the marker and/or sets the reconcile flag in one transaction. If either step fails, the app shows the failure message and makes no native write; the next boot retries only the `RKStorage` change. `node scripts/build-upgrade-harness.mjs` builds and signs the three harness APKs; `node scripts/check-upgrade-device.mjs <adb-serial>` runs the upgrade, JSON-backup import, damaged-database, missing-database, RN recovery, WebDAV sync, reminder-alarm and pending widget check-off scenarios on a phone (scenario 7: RN's alarm cancelled at the first native start and the native alarm set, once each, by `dumpsys alarm`; scenario 8: an RN user's pending widget check-off stored once at the first native start).
