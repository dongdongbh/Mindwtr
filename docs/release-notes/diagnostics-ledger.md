# Release diagnostics ledger

Maintainer file, not user docs. Every stable or RC release adds one log line per change that field testers are asked to confirm, and removes the previous release's lines once their issues are confirmed or closed; unconfirmed lines are carried forward under the new version. Complicated fixes add their line in the fix commit (AGENTS.md "Diagnostic log rides complicated fixes"); simple UI fixes need none; the release pass (`publish-release`, `publish-rc-release`) adds the rest and does the trim.

Convention: a release-specific line carries `extra.releaseCheck = "<version>/<slug>"` so it can be found with `git grep -n releaseCheck` and trimmed by version. General diagnostics (the sync trail, `[sync-encryption]` events, `Mobile background sync started`/`finished`, activation proofs) never carry `releaseCheck` and are never trimmed.

## General (keep)

- Sync trail: `Sync start`, `Sync step`, `Sync read check found no changes`, `Sync diagnostic complete` (core `sync-run.ts`, both apps). `Sync cycle requeued` carries `reason` and, since #1170, `detail` = the transport's own message (for a WebDAV 412: `WEBDAV_REMOTE_WRITE_CONFLICT: WebDAV document changed before replacement (412)`), so a server rejecting its own ETag shows in one line.
- `[sync-encryption]` state / remote-read / transition / error / activation (core + both apps).
- `Mobile background sync started` / `finished` / `run took longer than a minute` (`apps/mobile/lib/background-sync-task.ts`, #1001).
- `Mobile background sync registered` with interval (same file).
- `Mobile background sync registration checked` with `decision` (register | re-register | unchanged | unregister | deferred-until-foreground), `registered`, `storedInterval`, `interval`, `appState` (same file; a headless cold start must log `deferred-until-foreground`, never a re-register). Promoted from v1.2.7 after ltguillaume confirmed the background-job fix on 1.2.7 (2026-09-03).
- Desktop `Sync backend selected; running the verification sync to activate it` (`useSyncSettings.ts`).

- **`v1.2.8/attachment-only-task-replace`** — `packages/core/src/store-settings.ts`, in `fetchData`, once per store load (never per task) when `reconcileEntityCollection`'s new `attachmentOnlyReplacedCount` is greater than zero. Tester's log: on a device where a peer just changed or removed an attachment, this line proves the #1136 fix (e19270e0c) actually replaced the in-memory task instead of keeping the stale cached one, which is what caused the every-cycle resync #1136 reported (#1136, awaiting confirmation; #1156 may be a duplicate).

Tester's log: a phone whose server publishes an IPv6 address that drops connections showed `Sync failed … Cloud request timed out` exactly 30 s after `read-remote` in 1.2.7; with `connectTimeoutMs=10000` the read must now succeed over IPv4 within about ten seconds (#1150).
- **`v1.2.8/cloud-capture-accepted`** — `apps/cloud/src/server-capture.ts`, in `handleCaptureRequest`, just before the 201 response. Message: `Capture webhook request accepted`. Tester's log: a self-hoster whose capture script or watch posts to the webhook now has a server-side line proving the request arrived, even when nothing appears in the app (03e9cb9eb added the route without this line).
- **`v1.2.8/fence-mutation-horizon`** — `packages/core/src/sync-remote-fence.ts`, in `assertHeld`, after a successful renewal that leaves enough safe authority for the requested provider mutation. Tester's log: this line proves a client extended both the expiry and heartbeat reclamation window before a long remote mutation; its absence before a fence error means the provider could not confirm enough safe time.
- **`v1.2.8/section-conversion-canonical`** — `packages/core/src/store-tasks.ts`, in `convertTaskToSection`, after the task, section and checklist children are published in one store mutation. - **`v1.2.8/mcp-attachment-link-guard`** — `apps/mcp-server/src/service.ts` and `apps/mcp-server/src/cloud-service.ts`, after a guarded task or project link replacement has durably completed.
